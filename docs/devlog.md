# FinPath 개발 시행착오 기록

사회초년생이 목표를 고르면 실제로 필요한 돈과 모으는 순서를 계산해 주는 웹 서비스 FinPath를 3인 팀으로 만들며(2026-09-30 ~ 10-07) 겪은 시행착오를 정리했다.
작성자는 팀장(리포트 화면·전체 통합 담당)이고, AI 코딩 도구(Claude Code, Codex)와 함께 작업했다.

- 서비스: Next.js 정적 사이트(GitHub Pages), 서버 없이 브라우저에만 저장
- 협업: `main` 직접 수정 금지, 기능 브랜치 → PR → 자동 검사(형식·테스트·빌드) → 병합
- 결과: PR 30개, 자동 테스트 183개, 시연 인물 정하은(27세, 월급 245만 원, 마포구 월세 독립) 기준 시연

각 항목은 **언제 / 하려던 것 → 문제 → 고민한 선택지와 결정 → 결과와 배운 점** 순서다.

---

## 1. 자연어 입력을 먼저 만들었다가, 질문형 입력으로 중심을 옮김

**언제 / 하려던 것** — 9/30 ~ 10/1. 첫 설계는 사용자가 상황을 말로 적으면("다음 달 독립하는데 학자금이 2천 있어요") 규칙 해석기가 금액·시점을 뽑고, 빈 곳만 질문하는 구조였다. LLM이 조각을 나누면 그걸 값으로 바꾸는 정규화기(PR #5)도 따로 만들어 두었다.

**문제** — 실제 사용자 말투 문장 20개로 시험하니 8개는 해석하지 못하고 오류에서 멈췄다. "학자금 대출**이** 2천"을 조사 '이'까지 숫자 2로 읽어 **22,000만 원**으로 저장하는 버그도 나왔다. 질문에 답해도 지도에 반영되지 않는 질문(보증금, 계약 시기 등)도 많았다.

**선택지와 결정**
- 정규식 해석기를 계속 고친다 → 문장 유형이 끝없이 늘어서 시연 일정 안에 못 끝낸다고 판단
- LLM 해석기를 바로 연결한다 → API 키·비용·서버가 필요한데 정적 사이트 구조와 맞지 않음
- **질문 흐름을 먼저 탄탄하게 한다** (선택) → 해석기가 무엇이든 질문이 빈 곳을 메우게 하고, 해석기는 갈아 끼울 수 있게 자리만 남김

**결과와 배운 점** — 이해하지 못한 문장은 "상황 고르기"로 이어지게 하고(PR #6), 이후 기획안 v4에서 입력을 아예 질문형(①~③)으로 바꿨다. 발표 자료에도 "AI 해석기 미연결"을 한계로 솔직하게 적었다. **핵심 경험(입력 → 결과)이 해석기 품질에 매달리지 않게 설계해 두면, 어려운 부분을 나중으로 미룰 수 있다**는 걸 배웠다.

## 2. 스택 PR을 잘못 병합해서 계산 엔진이 main에 안 들어감

**언제 / 하려던 것** — 10/3. 입력 담당의 PR(#10) 위에 계산 담당이 계산 엔진 PR(#11)을 쌓았다(base = 입력 브랜치).

**문제** — #11이 `main`이 아니라 **입력 브랜치에 병합**되었고, 그 사이 #10이 먼저 main에 들어가서 계산 엔진이 main에 들어오지 못했다. 같은 시간에 리포트 v2(#12)도 다른 데이터 구조로 main에 들어가 있었다.

**선택지와 결정**
- #11을 되돌리고 다시 올린다 → 이미 다른 작업이 위에 쌓여 있어 꼬임
- **새 PR(#13)로 엔진을 main에 가져오면서 리포트 v2와 연결** (선택) → 양쪽 기능을 하나도 지우지 않는다는 원칙으로, 팀원 파일은 "추가만" 했다

**결과와 배운 점** — 입력(`/goal`의 답) 하나, 계산(`buildPlan`) 하나, 화면 여러 개로 데이터 흐름을 정리하는 계기가 됐다. **스택 PR은 base 브랜치를 병합 직전에 다시 확인해야 하고, 병합 순서를 팀에 미리 알려야 한다.**

## 3. 서비스 흐름 재배치와 "되돌릴 수 있는 장치"

**언제 / 하려던 것** — 10/3. 기획안 v4에 맞춰 화면을 ① 목표·내 돈 → ② 맞춤 질문 → ③ 정책 찾기 → ④ 타임라인 → ⑤ 리포트로 다시 배치했다(PR #14).

**문제** — 흐름을 크게 바꾸면 팀원들이 반대할 수 있었다. "의견이 갈릴 수 있으니 예전 것으로 돌아갈 수 있게 해 달라"는 요구가 나왔다.

**선택지와 결정**
- 예전 화면을 지운다 → 되돌리려면 코드를 다시 살려야 함
- **예전 흐름을 지우지 않고 스위치(`finpath.flow`)로 남김 + 병합 전 상태를 git 태그로 남김** (선택)

**결과와 배운 점** — 이후 큰 PR마다 `before-*` 태그를 남기고, PR 본문에 "되돌리기" 방법을 적는 습관이 생겼다. 실제로 PR #22를 되돌릴 때 이 습관 덕을 봤다(8번 항목). **큰 변경일수록 되돌리는 길을 먼저 만들어 두면 결정이 쉬워진다.**

## 4. 디자인: "금융 앱 같게"가 아니라 "따라 한 느낌 없이"

**언제 / 하려던 것** — 10/3. 화면이 "시중 앱·웹처럼" 보이게 디자인을 다시 잡으려 했다.

**문제** — 국내 금융 앱을 참고하면 지나치게 따라 한 느낌이 날 거라는 우려가 있었다.

**선택지와 결정** — 국내 금융 앱은 참고에서 빼고, 해외 서비스와 국내 비금융 서비스(Linear, Stripe, Apple 벤토 그리드, Notion, Typeform, Duolingo 등)를 분석했다. 색을 세 가지 의미(잉크·돈·부족)로만 쓰는 **Quiet Planner** 방향을 골랐다(`docs/design-direction.md`).

**결과와 배운 점** — 입력 화면은 다른 팀원 코드라 CSS만 덧붙이는 방식으로 바꿨고, `design.css` 한 줄을 지우면 예전 디자인으로 돌아가게 했다(PR #16). **남의 코드를 고치지 않고 덮어쓰는 층을 따로 두면 협업 충돌이 줄어든다.**

## 5. "처음부터 끝까지 무겁다" → 기능은 두고 묻는 양을 줄임

**언제 / 하려던 것** — 10/4. 직접 써 본 팀장 피드백: 결과 화면만이 아니라 처음부터 끝까지 무겁고 피로하다.

**문제** — 정하은 기준 질문이 24개였고, 목적과 상관없는 질문(결혼, 줄일 지출 등)까지 모두 물었다. 정책 목록도 입력 중간에 길게 나왔다.

**선택지와 결정**
- 기능을 잘라낸다 → 계산 정확도가 떨어짐
- **앞의 답에 따라 필요한 질문만 묻는 적응형 입력** (선택) — 고용 형태는 비상자금을 고른 사람만, 대출은 전세·매매이거나 보증금 3,000만 원 이상일 때만 묻는다. 결혼·빚 상환은 목적에서 빼되 엔진에는 남겼고, 정책은 입력이 아니라 타임라인 단계 안으로 옮겼다.

**결과와 배운 점** — 질문 24개 → 15개(PR #18). **"줄인다"를 "지운다"로 바로 바꾸지 않고, 언제 필요한지 조건을 붙이는 게 정확도와 가벼움을 같이 지키는 방법**이었다.

## 6. 타임라인을 세 번 다시 만듦 (요구를 잘못 읽은 경우 포함)

**언제 / 하려던 것** — 10/4. 단계별 할 일을 보여주는 타임라인.

**문제**
1. 처음엔 한 장씩 넘기는 카드 화면을 만들었는데, 원하던 건 **옆으로 누운 타임라인에서 카드를 누르면 크게 뜨는 화면**이었다.
2. 다시 만들었더니 이번엔 "마우스를 움직이면 화면이 따라오는" 동작을 원했다는 게 드러났다.
3. 상단 5단계 표시를 "고쳐 달라"는 말을 크기 문제로 이해해서 크게 키웠는데, 실제 지적은 **가운데 정렬이 안 된 것**이었다.

**선택지와 결정** — 가로 줄기 + 위아래 카드 + 화면 가운데 상세 창(방향키·밀기로 넘김)으로 바꾸고(PR #19), 마우스 따라가기를 넣었다. 상단 표시는 원래 얇은 막대로 되돌리고 가운데 정렬만 고쳤다.

**결과와 배운 점** — **말로 받은 화면 요구는 만들기 전에 그림(또는 예시)으로 한 번 확인해야 한다.** 이 경험이 8번 항목의 "하나씩 묻고 고치기" 원칙으로 이어졌다.

## 7. 리포트 팝업: 자동으로 띄웠다가, 껐다가, 다시 "한 번만" 띄움

**언제 / 하려던 것** — 10/3 ~ 10/5. 결과를 보는 첫 장면.

**문제** — 처음엔 타임라인에 들어가면 리포트 팝업이 자동으로 떴다. 그런데 "타임라인 보기"를 눌렀는데 리포트가 화면을 덮는다는 지적이 나와서 자동 팝업을 껐다(PR #21). 그러자 팀장은 "바로 뜨는 게 오히려 사용자를 붙잡는 장면"이라고 다시 원했다.

**선택지와 결정** — 큰 리포트 대신 **세 숫자 + 점수만 담은 짧은 요약 팝업**을 처음 한 번만(세션당 1회) 띄우고, 버튼 두 개(타임라인 따라가기 / 전체 리포트 보기)로 갈라지게 했다.

**결과와 배운 점** — 두 의견(덮지 말 것 / 바로 보여줄 것)이 둘 다 맞았다. **"보여줄지 말지"가 아니라 "무엇을 얼마나 보여줄지"로 질문을 바꾸면** 충돌하는 피드백을 함께 만족시킬 수 있었다.

## 8. 피드백 PR을 통째로 되돌리고, 항목별 확인으로 다시 만듦

**언제 / 하려던 것** — 10/5. 팀장의 피드백 20여 개(입력, 요약, 타임라인 내용, 리포트)를 한 번에 반영(PR #22).

**문제** — 병합 후 써 보니 의도와 다른 해석이 여러 개였다. 예:
- 헤더의 "뒤로"는 **5단계 중 한 단계 뒤로**, 아래 "이전"은 **질문 하나 뒤로**여야 하는데 둘 다 질문 하나 뒤로 만들었다.
- "저장"은 PDF가 아니라 **이미지로 저장**이었다.
- 이동 화살표 위치, 현재·권장 비교를 카드에도 보여줄지, 이사비를 보증금 단계와 합칠지 등도 달랐다.

**선택지와 결정**
- 틀린 부분만 덧칠한다 → 무엇이 확인된 것인지 섞여 버림
- **PR을 통째로 되돌리고(Revert, PR #23), 항목마다 선택지를 보여주고 답을 받은 것만 다시 적용** (선택, PR #24)

**결과와 배운 점** — 이후 화면 피드백은 항상 "선택지 2~4개 + 추천 + 미리보기"로 먼저 묻고 고쳤다. 되돌리기는 3번 항목의 태그·Revert 습관 덕에 몇 분 만에 끝났다. **빠르게 많이 만드는 것보다, 해석이 맞는지 먼저 확인하는 게 전체 시간을 줄인다.**

## 9. 타임라인 정보가 너무 복잡해짐 → 표현 방식을 하나로 줄임

**언제 / 하려던 것** — 10/6. 단계 상세에 금액 강조, 현재·권장 비교, 권장 문장 형광펜을 넣었다.

**문제**
- 한 화면에 구분 방식이 다섯 가지(주황·빨강·파랑 글자색, 노란 형광펜, 두 칸 비교, 범례, 번호 목록)라 복잡했다.
- 초록 칸의 이름표가 단계마다 현재·권장·목표·예상·지역으로 제각각이라 "권장 월 73만 원"이 무슨 뜻인지 알 수 없었다.
- 비교 줄이 나오는 단계와 안 나오는 단계의 기준이 화면에 드러나지 않았다.

**선택지와 결정**
- 금액은 굵게만, **줄어드는 돈만 빨강**. 형광펜은 단계당 한 줄 (PR #25)
- 초록 칸은 모든 단계에서 **"목표 | 해낼 일 + 숫자"** 한 가지 뜻으로 통일하고, 지금 값은 상세 창에 회색으로만 붙임 (PR #26)

**결과와 배운 점** — **강조 장치는 많을수록 강조가 사라진다. 같은 모양의 칸은 모든 곳에서 같은 뜻이어야 한다.**

## 10. 가상 인물 20명으로 결과의 타당성 점검

**언제 / 하려던 것** — 10/6. 신입·고소득·프리랜서·투자만·매매·전세 대출·적자·입주 임박/먼 미래 등 20명을 실제 입력 엔진에 넣어 타임라인과 리포트를 읽어 봤다.

**문제 (발견한 것 중 일부)**
- 2035년 입주라고 입력했는데 타임라인은 "목표 입주 2031년"으로 **앞당겨 버림** (돈이 모이는 달을 입주 달로 씀)
- 리포트의 "다 모으는 때"와 타임라인의 마련 시점이 서로 다름
- 저축률 0%인 사람에게 "청년 평균보다 **높아요**"라고 칭찬
- 쓰는 돈이 줄었는데 "늘고", 적자인데 "−26만 원으로 줄어요"
- 대출 2억 전세인데 "갚을 빚이 없어요, 100점"
- 월세 권장 상한 "6만 원 이하", 월급 330만 원에 "매달 2,447만 원 저축" 같은 비현실적 해결책
- 1억 넘게 부족한데 81점 '잘하고 있어요'

**선택지와 결정** — 방향을 정해야 하는 것만 사용자에게 물었다.
- 입주 날짜 → **입력한 날짜 유지**, 부족하면 "입주까지 ○○ 부족, 지금 속도면 ○월에 마련"
- 대출 이자 → **연 4%로 추정해 주거비에 더함**
- 비현실적 권장 → **숨기고 이유를 설명** (월세 30만 원 미만 권장은 "주거비와 생활비 함께 줄이기")
- 큰 부족 → 점수 감점 (11번에서 다시 조정)

**결과와 배운 점** — 회귀 테스트(`tests/persona.test.js`)로 같은 오류가 다시 생기지 않게 막았다(PR #27). **숫자가 맞아도 결과끼리 서로 다르게 말하면 사용자는 서비스를 믿지 않는다.** 화면 하나씩이 아니라 사람 한 명의 전체 결과를 처음부터 끝까지 읽어야 이런 모순이 보였다.

## 11. 팀원 피드백: "1억 목표가 0원으로 잡혀요", "250.5가 2,505로 들어가요"

**언제 / 하려던 것** — 10/7(제출일). 팀원이 직접 써 보고 네 가지 핵심 문제를 정리해 주었다. 같은 피드백을 Codex로 먼저 반영한 작업이 로컬에 커밋되지 않은 채 있었고, 그 위에서 이어서 작업했다.

**문제와 실제 원인**
| 제보 | 처음 추정 | 실제 원인 |
|---|---|---|
| 1억이 0원으로 잡힘 | 입력 상한이 3,000만 원 | 상한은 1,000억이었다. **"목돈 모으기" 목적이 없어서** 입력한 목표 금액이 비교용으로만 쓰였다 |
| 250.5 → 2,505 | 소수점 해석 오류 | 소수점(.)은 정상. **휴대폰 키패드의 쉼표 소수점 "250,5"**를 천 단위 쉼표로 읽었다 |
| 공유 링크에 월급·자산이 들어감 | — | 그대로 맞음. 링크에 프로필 전체가 담겼다 |
| 정책이 나이·지역만 봄 | — | 그대로 맞음 |

**선택지와 결정**
- 남은 목표 금액을 **'목돈 목표'**로 계산하고 타임라인 단계로도 보여줌
- 소수 입력은 받되, 결과 화면이 지저분해지지 않게 **결과는 만 원 단위 정수로 표시** (선택지: 소수 첫째 자리 / 정수 / 입력부터 정수만)
- 공유는 **기본 비공개**(목표 종류만), 금액 공개는 직접 체크
- 정책 소득·접수 기간 판정은 실제 공고 데이터와 세전 소득 입력이 필요해서, 제출일에는 **"추가 확인 필요"로 솔직하게 표시**하고 미룸

**결과와 배운 점** — PR #28. **버그 제보의 "증상"과 "원인"은 다를 수 있다.** 재현부터 하니 원인이 상한선이 아니라 목적 구조, 소수점이 아니라 쉼표였다. 다른 도구(Codex)가 만든 작업도 테스트를 돌리고 화면을 직접 확인한 뒤에 이어받았다. 그 과정에서 같은 문제(쉼표)가 여전히 남아 있는 것을 찾았다.

## 12. 2차 검토: "목표 달성 진단이 실제 시뮬레이션과 다르다"

**언제 / 하려던 것** — 10/7. 추가 검토에서 P1(심각) 3개, P2 2개가 나왔다.

**문제**
- 월급 300·저축 100·이사 후 월세 50, 목표 2,000만 원/24개월이면 실제 완료는 33개월인데 "기한 전에 모을 수 있다"고 나옴. **이사 전 저축액을 전체 기간에 적용**했기 때문
- 월세 180만 원을 입력한 뒤 저축을 290만 원으로 고치면 독립 후 지출이 −120만 원이 됨 (관련 답을 다시 검증하지 않음)
- 대출을 다 갚은 뒤에도 원금·이자가 계속 빠짐
- 소수 교통비 12.5만 원이 프로필에서 버려짐 (정수만 인정)

**선택지와 결정** — "기한까지 모을 수 있는 돈"을 **시뮬레이션과 같은 달별 흐름 함수 하나**(`monthlyFlow`)로 계산하게 했다. 독립 전 저축 → 독립 후 저축 → 대출 완납 후 늘어난 저축 순이다. 월급·저축을 고치면 "지금 내는 월세" 답을 재검증해서, 맞지 않으면 지우고 다시 묻는다.

**결과와 배운 점** — 같은 숫자를 두 곳에서 따로 계산하면 언젠가 반드시 어긋난다. **진단(리포트)과 시뮬레이션(타임라인)이 같은 함수를 쓰게 만드는 것**이 근본 해결이었다. 이자 감소는 반영하지 않아 결과가 조금 보수적(덜 모이는 쪽)이라는 한계는 문서에 남겼다.

## 13. 점수가 너무 낮다 → 감점 조정, 그리고 구조 문제 발견

**언제 / 하려던 것** — 10/7. 10번 항목에서 넣은 감점 때문에 시연 인물 정하은이 54점 '조금만 더 해봐요'가 나왔다.

**문제** — 감점 숫자만 줄여 보다가 구조 문제 두 개를 발견했다.
1. **같은 걸 두 번 깎았다.** '목표 준비도' 항목이 이미 "필요한 돈의 78%"를 점수로 매기는데, 기한 부족 감점이 같은 78%로 또 깎았다.
2. **저축률을 독립 후 기준으로만 봤다.** 지금 월급의 29.8%를 모으는 사람이 독립 후 4.9% 기준으로 25점 중 3.5점을 받았다.

**선택지와 결정** — 제출일이라 큰 개편 대신 **"하나만 고친다면 효과가 가장 큰 것"**을 골랐다. 감점을 절반으로 줄이고, 저축률은 **지금과 독립 후의 평균**으로 매기고, 점수 카드에 "지금 29.8% · 독립 후 6.9%"를 함께 보여줬다(PR #29). 감점 중복 해소와 점수를 '습관'과 '목표 진행'으로 나누는 개편은 다음 과제로 남겼다.

**결과와 배운 점** — 정하은 54점 → 67점 '잘하고 있어요'. 1억 넘게 부족한 사람은 여전히 감점과 최고 등급 제한을 받는다. **점수 조정은 숫자 튜닝보다 "무엇을 재는지"를 먼저 의심해야 한다.**

## 14. 발표 자료와 실제 화면 맞추기

**언제 / 하려던 것** — 10/7. 발표 자료(14장)와 배포된 화면을 비교했다.

**문제** — 병합 후 질문 수(16 → 18개)와 테스트 수(163 → 183개)가 바뀌었다. 공유 설명("링크에 숫자가 담겨요")과 월세 상한 예시(73만 원; 화면은 55만 원)도 화면과 달라졌다. 다른 AI가 생활비 증가 33만 원·지금 월세 20만 원을 넣자고 제안했는데, 그러면 모든 시연 숫자(1,899만 → 1,938만 원 등)가 바뀌었다.

**선택지와 결정** — 발표 자료를 크게 고치지 않기로 하고, **본 발표 슬라이드에서 달라지는 숫자 두 개만** 고쳤다. 나머지는 질의응답 때 말로 답하기로 했다. 시연 입력은 자료와 같은 숫자가 나오는 0/0으로 정했다. 33/20 안은 "20만 원은 원래 부모님 용돈"이라 질문받기 쉬운 가정이어서, 질의응답용 설명으로만 남겼다.

**결과와 배운 점** — 배포 사이트에서 발표 순서 그대로 PC·휴대폰 확인 38개를 돌려 화면 숫자를 대본과 맞췄다. **시연 숫자는 코드 변경 하나에도 움직이므로, 제출 직전에는 "발표 자료 기준 숫자"를 테스트로 고정해 두는 게 안전하다.**

## 15. 계정 이름 변경으로 데모 주소가 404가 됨

**언제 / 하려던 것** — 10/7. GitHub 계정 이름에 개인 정보가 드러나서 계정 이름을 바꿨다.

**문제** — 저장소 주소는 GitHub가 새 주소로 넘겨 주지만, **GitHub Pages 주소는 넘겨 주지 않아** 예전 데모 주소가 404가 됐다. README와 발표 자료에 예전 주소가 남아 있었다.

**선택지와 결정** — 새 주소에서 전체 시연 흐름과 직접 주소 접속·새로고침·인쇄·공유를 다시 점검하고, README 주소를 고쳤다(PR #30). 커밋 기록에 남은 예전 이름은 기록을 다시 써야 해서 제출 후 과제로 미뤘다.

**결과와 배운 점** — **공개 저장소의 계정 이름·커밋 정보도 개인 정보다.** 처음 만들 때부터 개인 정보가 없는 계정 이름을 쓰는 게 가장 싸다.

## 기술적으로 오래 걸린 문제들

| 문제 | 원인 | 해결 |
|---|---|---|
| 로컬 빌드가 Windows에서 실패 | 이 Next.js 버전의 Turbopack이 Windows 환경에서 막힘 | `next build --webpack`으로 빌드, 배포는 CI에서 |
| Pages 배포 후 링크가 깨짐 | 저장소 이름 하위 경로(`/FinPath`)에서 서비스됨 | 배포 빌드에서만 `basePath`·`trailingSlash`를 켜고, 공유 링크도 같은 기준으로 만듦 |
| 셸에서 스크립트로 코드를 고치면 정규식 역슬래시가 사라짐 | bash heredoc·`node -e` 안의 이스케이프 처리 | 정규식이 들어간 수정은 편집 도구나 별도 스크립트 파일로 |
| 같은 문자열 치환이 두 번째부터 실패 | Prettier가 줄바꿈을 바꿔 놓음 | 치환 전에 실제 파일 내용을 다시 읽고 고침 |
| 팝업 안의 공유 창에서 Esc를 누르면 바깥 팝업까지 닫힘 | 중첩 `<dialog>`의 cancel 이벤트 전파 | 안쪽에서 전파를 멈추고, 바깥은 `event.target`이 자기 자신일 때만 닫힘 |
| 이미지로 저장한 파일 이름이 하루 전 날짜 | `toISOString()`이 UTC 기준 | 로컬 날짜로 파일 이름 생성 |
| 브라우저 자동 점검이 가끔 시간 초과 | 애니메이션 중 클릭, 여러 점검을 한 서버에 동시에 실행 | 점검을 하나씩 실행하고 화면이 멈춘 뒤 클릭 |
| 공유 링크에 개인 정보 | 서버 없이 링크 안에 프로필을 담는 구조 | 기본은 목표 종류만, 금액 공개는 사용자가 선택 |

## 돌아보며

- **되돌리는 길을 먼저 만든다.** 태그·Revert·흐름 스위치 덕에 큰 변경도 부담 없이 시도하고 되돌렸다.
- **해석을 먼저 확인한다.** 화면 피드백은 선택지와 미리보기로 묻고 나서 만들었을 때 다시 만드는 일이 사라졌다.
- **같은 숫자는 한 곳에서 계산한다.** 리포트와 타임라인이 다른 계산을 쓸 때마다 모순이 생겼다.
- **사람 한 명의 결과를 끝까지 읽는다.** 단위 테스트가 다 통과해도 가상 인물 20명의 결과를 읽어야 보이는 오류가 있었다.
- **모르는 건 모른다고 표시한다.** 정책 자격, 지역 물가, 대출 이자 감소처럼 데이터가 없는 부분은 "추가 확인 필요", "추정"으로 화면에 밝혔다.
